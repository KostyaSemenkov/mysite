## Источники и границы сбора

- Kimi: `https://www.kimi.com/en/blog/`, `https://platform.kimi.ai/blog`, `https://platform.kimi.ai/blog/posts/changelog`.
- Z.ai: `https://docs.z.ai/release-notes/new-released` — журнал выпусков, не весь исследовательский блог.
- Qwen: `https://qwen.ai/api/v2/article/retrieval?type=qwen_ai&language=en-US`; читательские ссылки `https://qwen.ai/blog?id=...`. Это публичные данные сайта, а не платные запросы к модели. Старый архив page_config не использовать вместо текущей ленты.
- DeepSeek: `https://api-docs.deepseek.com/updates/`, записи выделяются по датам.

Парсеры привязаны к структуре официальных страниц. При её изменении нужна диагностика и корректировка, а не подмена источников сторонними новостями. Для Kimi уже исправлялась ошибка выбора родительской карточки, связывавшая заголовок со ссылкой соседнего материала; есть регрессионный тест.

Фильтрация заголовков эвристическая. Сборщик не отслеживает каждую таблицу тарифов и все незаявленные изменения документации. Ранее импортированные записи проверяются, пока доступны в выдаче источника. Сохранённый `.source-cache` — исторический материал, не источник текущих фактов.

## Редакционный процесс и гарантии

Новая запись получает `waiting`, оригинал, дату и ссылку. Первые 16 русских изложений подготовлены вручную при разработке. Будущие автоматически не переводятся.

После заполнения русских полей редактор нажимает «Текст готов к проверке» (`review`), затем «Одобрить и опубликовать». Для публикации нужны права на добавление/изменение Publication. Изменения выполняются POST-запросами с CSRF-защитой. Черновики и оригиналы не видны публично.

Изменение оригинала сохраняет предыдущий текст и переводит запись в `changed`, сохраняя прежний русский текст и опубликованную версию. Нужно проверить актуальный оригинал и повторно одобрить. Повторная публикация обновляет ту же Publication, не создаёт дубль. Отклонение черновика не снимает уже опубликованную версию с сайта.

В формах редактирования и предпросмотре есть проверка версии записи, чтобы изменение источника или редакторского текста после открытия страницы блокировало устаревшее действие. Есть групповые действия в стандартной админке.

## Запуск и расписание

Восстановление окружения и запуск описаны в `START_HERE.md`. Для Linux используются те же команды через `.venv/bin/python`; Windows `.cmd` и `.ps1` на Linux не применяются.

Разовый сбор после выбора основной рабочей базы:

```powershell
.\.venv\Scripts\python.exe manage.py import_china_news
```

Есть параметры `--source kimi|zai|qwen|deepseek` и `--initial-limit 3..5` (по умолчанию 4). Сборщик запоминает непринятый старый архив, не импортирует его весь при повторных запусках, не публикует и не вызывает платные LLM.

Существующая задача Windows: `NEYRO-China-News-Hourly`, pythonw.exe из исходного `.venv`, запуск `scripts/run_news_job.py`, интервал час, лимит 30 минут, параллельный запуск игнорируется. Работает при вошедшем пользователе, включённом компьютере и доступной сети. Задание не перенесётся из архива автоматически. Состояние — `SCHEDULER_STATE.json`.

Установщик не заменяет чужую задачу с тем же именем/другим путём. При смене каталога не обходить эту проверку: сначала определить, какой экземпляр остаётся основным, и согласованно перенастроить расписание. Упаковка существующее расписание не выключала.

## Следующий этап: Cloud.ru

Обсуждалась одна Linux VM с публичным IP, ориентир 2 vCPU, 4 ГБ RAM, 30–40 ГБ диска. Это предварительная оценка, не оплаченный заказ; цену и доступные образы нужно проверить на момент развёртывания. Домен и доступ к Cloud.ru ещё не предоставлены. GPU не нужен.

Предлагаемая последовательность:

1. Уточнить домен, наличие аккаунта/сервера, бюджет и способ предоставления доступа. Не просить присылать пароль или приватный SSH-ключ в чат.
2. Подготовить конфигурацию Gunicorn + Nginx, systemd для сайта и таймер для сборщика. Production-файлов/Dockerfile/CI в этом проекте пока нет.
3. Настроить DEBUG=0, новый секрет, ALLOWED_HOSTS, домен, HTTPS, доверенную обработку прокси-заголовков и статику (`collectstatic`). `.env` автоматически не загружается текущим кодом: переменные задаются реальным окружением процесса.
4. Сохранить свежую базу из действующего экземпляра. Этот архив — снимок на дату упаковки, поздние изменения в него не попадут. Для небольшого старта допустимо оставить SQLite; PostgreSQL потребует драйвера, настроек, переноса и проверки данных.
5. Удалить/заменить демоматериалы для публичного запуска, согласовать название и реальные контакты редакции. Не снимать флаг demo, выдавая примеры за реальные новости или курсы.
6. Настроить резервные копии отдельно от VM, проверить восстановление, журналы и автозапуск.
7. Выполнить `manage.py check --deploy` с production-настройками и проверить HTTPS, вход, статику, получение черновиков. Публиковать реальные новости только по решению пользователя.
8. После проверенного переноса выключить локальный сборщик и включить единственное серверное расписание. Не вести две независимые редакционные базы.

Текущий `runserver` — только локальная разработка. Читательских кабинетов, платежей, хранения уроков и автоматического русского перевода нет. Не добавлять их без отдельной задачи.

## Сохранность комплекта

Базы получены SQLite backup API; сессии очищены только в копиях, затем выполнена проверка целостности. Хеш пароля и пользовательские записи сохранены для миграции; набор не предназначен для публичной публикации. Исходный проект, база, пароль редактора, публикации и задание Windows при упаковке не изменялись.

Проверить целостность архива можно по соседнему файлу `.zip.sha256`, а содержимое — по `MANIFEST.sha256`. Скриншоты и старые журналы показывают состояние на время их создания; актуальные сведения при упаковке — в JSON и отчёте проверок.
